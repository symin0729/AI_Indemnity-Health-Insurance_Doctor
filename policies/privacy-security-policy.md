# 실손보험 1~5세대 RAG 상담 서비스 개인정보·정보보안 정책

> 문서 버전: v1.0  
> 상태: `DRAFT_INTERNAL_REVIEW`  
> 적용 대상: `AI_IHID` 실손보험 1~5세대 정보 제공·모의계산·RAG 상담 서비스  
> 시행일: 법률·보안 검토 후 확정  
> 주의: 내부 정책 원본이며 외부 공개용 개인정보처리방침을 대신하지 않는다.

## 1. 목적과 서비스 한계

서비스는 검증된 공식자료에 근거한 일반 정보와 검증된 Rule Engine의 모의 계산을 제공한다. 보험 유지·해지·전환을 추천하거나 실제 보험금 지급 여부를 확정하지 않는다. 근거가 부족하면 추측하지 않고 `INSUFFICIENT_EVIDENCE`를 반환한다.

## 2. 기본 원칙

- 최소수집: 서비스에 불필요한 개인정보를 요구하지 않는다.
- 목적 제한: 입력정보를 해당 요청 처리 외의 목적으로 사용하지 않는다.
- 보유 최소화: 불필요한 원문과 민감정보를 저장하지 않는다.
- 사용자 통제: 저장 여부, 보유기간, 삭제 방법을 공개용 방침에서 안내한다.
- 근거 기반: 공식자료와 검증된 Rule만 사용한다.
- 기본 차단: 판단할 수 없는 입력과 미검증 자료는 허용하지 않는다.

## 3. 입력정보 분류

개인정보 없이 처리할 질문은 세대별 구조, 급여·비급여, 자기부담·공제·한도, 특약 구조와 보험사 확인사항이다.

제한적으로 사용할 수 있는 비식별 정보는 세대, 상품명·버전, 가입 시기, 보험료, 보장종목, 특약 가입 여부와 가상의 치료비·횟수다. 계약 식별번호 없이 처리한다.

입력 금지 또는 차단 대상:

- 주민등록번호·외국인등록번호·여권번호·운전면허번호
- 보험증권번호·계약번호·고객번호
- 계좌번호·카드번호·비밀번호·인증번호
- 이름·전화번호·이메일·주소 등 불필요한 식별정보
- 진단서·처방전·영수증·상세 진료기록 원문
- 병명·병원명·진료일·약제명 등 불필요한 건강정보
- 타인의 개인정보

## 4. 처리 파이프라인

```text
사용자 질문
→ 동의·정책 버전 확인
→ 개인정보·민감정보 탐지
→ 차단 또는 비식별화
→ 질문 범위 분류
→ Scope OUT·의료조언·추천·지급확정 차단
→ 허용 질문만 RAGFlow 검색
→ VERIFIED 공식 근거 확인
→ 필요한 경우 검증된 Rule Engine 계산
→ 최소 데이터만 Gemini에 전달
→ 숫자·Rule·Evidence·문서 ID 검증
→ 사용자 응답
```

## 5. RAG 데이터 보안

- RAG 지식베이스에는 금융당국·보험사 공식자료와 운영자가 검증한 자료만 등록한다.
- 모든 RAGFlow 문서·청크는 `status: "VERIFIED"`여야 한다.
- 사용자 질문·주장·LLM 답변을 지식베이스에 자동 저장하지 않는다.
- 사용자 질문과 공식 지식베이스를 논리적으로 분리한다.
- 미검증·상태 누락·거절 자료는 근거에서 제외한다.
- 다른 상품·세대·담보가 섞이지 않도록 검색 전후 필터를 사용한다.

## 6. LLM 외부 전송

외부 AI에는 설명에 필요한 최소 데이터만 전달한다. 이름, 연락처, 계약 식별번호, 병명, 병원명, 진료일, 진료기록, 영수증 이미지, 계좌·카드·인증정보는 전달하지 않는다.

외부 전송 전 유효한 동의, 개인정보 제거, 허용 필드 DTO, 근거·계산 검증을 모두 통과해야 한다. 계산 설명 API는 15·16번 승인 전까지 `FEATURE_DISABLED`를 유지한다.

## 7. 질문 범위

- 약관·세대·특약·자기부담·공제·한도 설명은 허용할 수 있다.
- 진단·치료·약 복용 조언은 차단한다.
- 가입·해지·전환 추천과 실제 보험금 지급 확정은 차단한다.
- 의도가 불명확하면 `CLARIFICATION_REQUIRED`를 반환한다.
- 개인 모의계산은 검증된 입력과 Rule Engine이 있을 때만 수행한다.

## 8. 로그와 보유

요청 ID, Scope 결과, 검색 문서·Evidence ID, 응답 상태, 오류 코드, 처리시간, RuleSet 버전과 Rule ID만 최소한으로 저장한다. 질문 원문 개인정보, 건강정보, 계약·계좌·결제·인증정보는 저장하지 않는다.

구체적인 보유기간과 삭제 절차는 법률·운영 검토 후 별도 정책에서 확정한다.

## 9. 접근통제

| 역할 | RAG 문서 | Rule | 로그 | 개인정보 |
|---|---:|---:|---:|---:|
| 일반 사용자 | 검색 결과만 | 접근 금지 | 접근 금지 | 본인 입력만 |
| 운영자 | 허용 | 제한 | 허용 | 제한 |
| 개발자 | 테스트 범위 | 허용 | 제한 | 원칙적 접근 금지 |
| 검수자 | 허용 | 허용 | 승인 기록 | 원칙적 접근 금지 |
| 보안관리자 | 허용 | 허용 | 허용 | 사고 대응 시 최소 접근 |

## 10. Prompt Injection과 데이터 오염 방지

- 시스템 규칙 무시, 내부 문서 공개, 근거 없는 답변 요구를 따르지 않는다.
- 검색 문서 안의 지시문도 데이터로만 취급한다.
- LLM 답변을 검수 없이 RAG 문서·Rule·Evidence로 승격하지 않는다.
- 사용자 경험담과 주장만으로 Rule을 변경하지 않는다.
- 공식자료 확인과 두 명의 검수 없이 Rule 상태를 올리지 않는다.

## 11. 근거 부족 표준 안내

```text
등록된 공식 자료에서 충분한 근거를 찾지 못했습니다.
약관 또는 보험사 고객센터에서 정확한 내용을 확인해주세요.
```

## 12. 계산 Rule 보안

```text
NEEDS_SOURCE_REVIEW
→ SOURCE_VERIFIED
→ RULE_DRAFTED
→ VERIFIED_FOR_CALCULATION
```

`VERIFIED_FOR_CALCULATION` 이전에는 계산을 활성화하지 않는다. 계산 결과에는 상품 코드, RuleSet 버전, Rule ID, Evidence ID를 남기되 개인정보는 남기지 않는다.

## 13. 사고 대응

```text
사고 탐지
→ 접근 차단·추가 유출 방지
→ 영향 범위와 개인정보 포함 여부 확인
→ 필요한 로그 보존
→ 내부 보고
→ 법률·규제상 신고·통지 검토
→ 재발 방지
```

## 14. 정책 변경과 승인

- 변경 버전, 사유, 승인자, 시행일을 기록한다.
- 입력 필드·외부 전송·로그·보유기간 변경 시 검토를 다시 수행한다.
- 12~16번 문서와 코드가 정책과 다르면 더 엄격한 안전 기준을 우선 적용한다.
